## 总判断

你的项目问题不是"某个文件写得乱"，而是**同一套工程里并存两套互相打架的屏幕范式，且迁移做了一半就停住**——留下大量"声称要做什么但没人用"的结构体字段、根本编不过的散文件、和复制了三四遍的组件。重构的收益不在"重写"，而在"收敛范式"。

---

## 重点一：屏幕导航范式必须收敛（影响面最大，最先做）

现在有两套并存：

- **范式 A — tileview 内嵌**：`screen_manager.c` 把表盘/工具/卡片/应用列表/消息 5 个面板挂进 tileview，每屏提供 `xxx_create(self, parent)`，状态写入 self 结构体。这是你做得相对好的一部分。
- **范式 B — 独立全屏**：运动详情页（`event.c` 的 `panel_t`）、设置页（`setting_page.c`）、音乐页（`music.c`）都用 `lv_obj_create(NULL)` + `lv_scr_load()`，隐藏旧屏、右滑返回。

冲突的直接证据：

1. **结构体字段和真实实现脱节**。`screen_card.h` 里声明了 `main_scr / sport_scr / compass_scr` 三个字段（注释写着"进入详情页前的活动屏幕/详情页根对象"），但全工程**从未赋值、从未使用**；实际跳转走的是 `event.c` 的全局 `panel_t sport_panel` 和 `setting_page.c` 的全局 `setting_page`。这是"迁移到一半"的实锤。
2. **同一"点击进详情页"语义有三种实现**：`sport_btn_click_cb` / `compass_btn_click_cb`（event.c）、`setting_btn_click_cb`（setting_page.c）、`panel_click_cb`（event.c）。
3. **右滑返回有两套手势回调，逻辑还不一样**：`screen_switch_gesture_cb`（user_data 里存 old_scr）vs `setting_panel_gesture_cb`（全局 `setting_page` + user_data 存 old_scr）。
4. **"让子孙事件冒泡"的递归函数复制了 4 份**：`screen_manager.c`（被注释掉）、`screen_main.c` 的 `compass_event_bubble_all`、`event.c` 的 `gesture_bubble_all`、`setting_page.c` 的 `setting_gesture_bubble_all`。同一个工具函数四个实现。

**怎么收敛**：推荐保留 tileview 作主骨架（表盘滑动体验依赖它），把"需要全屏沉浸的详情页"（运动/指南针/设置/音乐）统一收进一个 `ScreenManager`，提供 `push(page)` / `pop()` 两个接口，所有"点哪进详情页"都走同一入口，手势返回由 manager 统一注册。删掉上面三处分散的回调。不要两种范式继续混用——那是当前一切混乱的根源。

## 重点二：页面生命周期没有管理 = 嵌入式上的内存泄漏

所有详情页都是"隐藏旧屏 → load 新屏 → 返回时再隐藏/恢复"，**页面对象从不销毁**。反复进出时 LVGL 对象树里对象只增不减，`LV_OBJ_FLAG_HIDDEN` 只是不渲染，对象、样式、observer 全占着内存。在 ESP32-S3 上这是实打实的泄漏。

**怎么改**：把详情页当"动态屏幕"——进入时创建，返回时 `lv_obj_delete()` 销毁。因为数据都由 `data_center` 的 subject 驱动，重建 UI 是零状态成本，反而比长期缓存更省内存。如果确实想缓存，就让缓存只有**一个权威来源**（集中在 ScreenManager），而不是 `setting_page.c` 自己存一份全局 `setting_page`、`event.c` 的 `panel_t` 又存一份 `base`。

## 重点三：重复实现的组件要抽出来（罗盘、运动圆环、按钮）

**罗盘被复制了两份**：
- `screen_main.c`：4 段弧 + 4 方向标签 + 旋转容器，一堆文件级 `static` 全局（`compass_rot/compass_arc[4]/compass_label[4]`）。
- `compass_panel.c`：2 段弧 + 2 标签 + 另一套 `static` 全局，且 `compass_panel_create` 是 `static`、**没有对外入口**——大概率是死代码/没接上。

这两份应该抽成一个 `compass_widget`：`compass_widget_create(parent, 段数, 方向表)`，把控件打包进**它自己的 context 结构体**（而不是文件级 static），暴露 `compass_widget_set_heading(w, deg)`。你现在文件级 static 的设计注定了"一个文件只能存在一个罗盘实例"，未来要第二块罗盘就崩。

**运动圆环同样被复制**：`artivity_rings_create` 本意是复用的，但 `sport_panel.c` 直接引用了 `artivity_rings_t`、`label_data_t`、`sport_max`、`data[]`、`sport_maxs[]`、`label_update_cb`——**这些全是 `sport_card.c` 里的 static / 未导出符号**，`sport_panel.c` 根本编不过。它是一份从卡片复制过来改到一半的残骸。圆环 + 数值标签应抽成独立组件（`activity_rings_widget` + `stat_label`），直径/满量程/颜色/subject 全部由配置数组传入，两处共用。

另外 `Button_t` 定义在 `screen_manager.h` 里（"屏管理"头文件里放通用控件类型，职责错位）；且 `screen_app.c` 里 `applist[i].label` 实际存的是**可点击的容器对象**，不是 label——字段名和语义对不上。通用控件应挪到独立的 `ui_widgets.h`。

## 重点四：状态管理三种写法并存，收敛成一种

现状三种混用：
1. **结构体实例传入**（对）：`screen_main/card/tools/app` 的 `xxx_t self`。
2. **文件级 static 全局**（要收）：`screen_main.c` 的罗盘、`screen_tools.c` 的 `title_style`、`HRmonitor.c` 的 `low_values/high_values/value_index`、`screen_manager.c` 的 `g_tileview/g_tile_index`。
3. **跨文件裸全局**：`g_tileview`（extern 在 screen_manager.h，但几乎没人用）、`music_panel`（music.c 非 static 导出、无人消费）、`panel_t sport_panel`（extern）。

几个具体问题：
- **`HRmonitor.c` 的 `static Uint8 value_index`**：`Uint8` 是 SDL 类型，应统一 `uint8_t`。更本质的是 `low_values/high_values/value_index` 是"这根柱子的数据状态"，却跟具体 chart 对象解耦——未来存在第二个 HR chart 实例就会串数据。这正是"组件状态不该放文件级全局"的反例。
- **`screen_card_t.arc_obs[3]`** 注释写"便于统一移除"，确实被写入，但**从不读取**。而且它用的 `lv_subject_add_observer_obj()` 本来就绑定对象生命周期、对象删除自动移除 observer——这个存储字段纯属冗余设计，要么删掉要么真实现删除逻辑。
- **`g_tileview`/`g_tile_index`** 是"公开了但没人用"的全局，`g_tile_index` 自己注释都写了"暂未使用"。

**收敛原则**：属于"一个 UI 组件实例"的状态 → 进该组件的 struct（create 时分配/传出）；属于"整个 app"的状态 → 进显式 App 上下文或 data_center；文件级 static 只留给编译期常量和模块私有工具函数。

## 重点五：数据层——subject 注入 + 把散落的规则/常量收进 data_center

你用了 LVGL 9 的 subject/observer，方向很对（数据源与 UI 解耦），但还有三点：

1. **subject 绑定写死**：`sport_card.c` 里 `static lv_subject_t *data[] = {&g_calorie_subject, ...}` 是文件级数组，组件创建时硬编码。建议 create 接口把 `lv_subject_t **subjects` 作为参数传入（依赖注入），组件才能绑不同数据源、也才能被单测。
2. **同一规则多处复制**：电量图标分级逻辑实现了两遍——`screen_main.c` 的 `bat_symbol_get()` 和 `screen_tools.c` 的 `bat_observer_cb` 内联 if-else。应抽成 data_center 的统一函数 `const char *bat_symbol_level(uint8_t bat)`。
3. **满量程魔法数散落**：`400/6000/1200` 出现在 `sport_card.c` 的 `sport_maxs[]` 和圆环 configs 里，而 `screen_main.c` 用的是 `CALORIE_MAX`（来自 data_center）——同一语义两种写法。这些业务阈值应统一放 data_center 命名常量（`CALORIE_MAX/STEPS_MAX/DURATION_MAX`），UI 只引用常量，避免"改一个忘一个"。

另外一个职责倒挂：`HRmonitor.c` 在 UI 创建函数 `HR_table_create()` 末尾直接调 `data_center_hr_sample()` 触发采样。**UI 不该驱动数据采集**，采样应由 core 层定时器/事件驱动，UI 只消费 subject。

## 重点六：先清理死代码/编译不过的残留，重构才安全

这些都是确定性问题：

| 文件 | 问题 |
|---|---|
| `sport_panel.c` | `sport_panel_creata` 用了**未定义变量 `self`**，引用 sport_card.c 的 static 符号；头文件声明 `(screen_card_t*, lv_obj_t*)` 与 .c 定义 `(lv_obj_t*)` 签名不一致——**必然编不过** |
| `event.h` | `struct panel` 体内 `void (*panel_create)(panel_t)` 引用了尚未定义的 typedef 别名 `panel_t`，严格 C 下报 `unknown type name`；且该字段从没被调用 |
| `event.c` | `panel_click_cb` 里 `if(panel->base)` 写在 `panel->base == NULL` 分支内，恒为 false，死代码 |
| `music.c` | `music_play_create` 建了 label 但没注册到任何屏、没被调用（music.h 里连函数声明都没有）；文件系统扫描（`scan_music_folder/is_audio_file`）混在 UI 文件里，应移入 core 数据层 |
| `compass_panel.c` | `compass_panel_create` 是 static 无对外入口，整个文件可能没接入构建 |
| `screen_app.c` | 大量注释代码；`app_cb[]` 只有最后 2 个有回调，其余 8 个 NULL（点了没反应） |
| `HRmonitor.c` | `HR_btn_click_cb` 空实现 |

建议重构第一步就是"摘掉这些编不过/未接入的文件，建立可编译基线"，否则你改架构时会被这些半成品反复牵制。

## 重点七：低成本规范（可穿插做）

- **include guard 统一**：现在混着 `SCREEN_APP_H` / `__SCREEN_MAIN_H` / `__HR_MONITOR_H` / `CARD_H` / `__SETTING_PAGE`（缺 `_H`、双下划线是编译器保留）/ `__SPROTY_PANEL`（拼错）。统一为 `模块名_H`，别用双下划线开头。
- **拼写**：`palymode_t→play_mode_t`、`artivity→activity`、`arc_boserver→arc_observer`、`sport_panel_creata→create`。
- **样式统一**：现在一半走 `style/app_styles.h`，一半每个文件内联 `lv_style_init` 模块级 static（`applist_style`/`title_style`/`sport_label_style`/`setting` 的 `title_style`）。模块级单例若 create 被调多次会重复 init。要么全进 app_styles，要么给通用样式（按钮/标题/列表项）建统一入口。

## 目标架构（简版）

```
app/           组装层：init、主循环、唯一导航 ScreenManager
ui/
  screens/     每个屏幕一个文件，统一 create(self, parent) 签名（表盘/工具/应用/卡片）
  pages/       全屏详情页，ScreenManager push/pop，返回即销毁（sport/compass/setting/music）
  widgets/     可复用组件，状态进各自 struct、无文件级 static
               compass_widget  activity_rings  stat_label  battery_icon  title_bar
core/
  data_center  所有 subject + 业务常量 + 分级规则（bat_symbol_level 等）
  sensors/media/fs   HR 采样、音乐扫描等非 UI 逻辑
style/  utils/
```

核心就三条纪律：**导航只有一个出口**（push/pop，返回即销毁）；**组件不持有文件级全局**（状态进 struct，谁创建谁持有）；**UI 不碰业务**（subject 是唯一数据通道，阈值/规则在 core）。

1. **清理死代码**（重点六），建立可编译基线
2. **抽 ScreenManager**，统一三处跳转 + 两套手势返回（影响面最大，最先做）

4. **把电量分级、满量程常量收进 data_center**，UI 改引用常量
